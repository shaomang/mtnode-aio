# Deliverable node (deliver)

The human landing spot that the **long-running task** system leaves on the main canvas. It looks
like a file node, but you cannot add it by hand: only an enabled long-running task creates it, and
it is created with a system **uid** bound to a fixed directory.

## What it is for

Some steps inside a long-running task can only be done by a person: approve a draft, or hand over
material (a final text, a set of images, a decision). Such a step shows up on the canvas as a
deliverable node.

### One terminal, exactly one file

This is the core rule of the node: **every file that has not been delivered yet is one input
terminal**.

- The terminal's label **is that file's name** (e.g. `storyboard.md`), so a wire tells you at a
  glance which file it feeds.
- The top of the node renders a **Markdown table** naming, row by row, what each terminal's file must
  contain:

  | File name | What goes in it | Required/Optional | Format or size | Delivery status |
  | --- | --- | --- | --- | --- |
  | storyboard.md | shot size / duration / dialogue / camera move per shot | Required | .md only · ≤ 2 MB | Pending |

  Above the table sits **▤ Preview Markdown**: it opens the whole checklist in the **in-app Markdown
  previewer** — the on-disk `交付清单.md` (the full human-readable document) when it exists, otherwise
  this very table. The previewer has its own "copy all" button, so pasting it to a teammate also
  happens in that window (the node no longer carries a separate copy button).
- **Once a file is delivered, its terminal disappears** and the remaining terminals close the gap;
  existing wires follow the file they belong to (re-bound by file item id), never drifting onto a
  neighbour.
- Text / choice entries have no file and therefore no terminal — fill them in on the strip.

### Two places edit the list; the canvas wins

- The initial list comes from the human step in the task graph (`human.deliver.items`).
- You can also edit it on the node itself: **＋ Add file** takes a file name / description /
  required flag / format-or-size note, and every terminal can be deleted.
- **After you edit, the canvas version wins**: the system only appends new entries from the graph, it
  never overwrites your edits with the old list. Changes are written back to the graph definition,
  `manifest.json` and `交付清单.md`.

### What the node shows

- Header: **checklist progress** (`Delivered 3/5`) plus a hint to handle the step on the strip.
- Middle: the Markdown table above, then **terminal rows** (one row per pending terminal with its own
  upload and delete buttons), then the **delivered section** (what was handed in, from where, when),
  each with a **Revoke** button.
- The delivery folder is generated by the system: `<workflow workspace>\mtnode-deliverables\<uid>\`,
  containing `manifest.json` (machine source of truth) and `交付清单.md` (for humans). If the
  workspace is unavailable it falls back to `%APPDATA%\pipeline-console\longtask\deliver\<uid>\`
  and tells you once.

## Two ways to deliver

1. **Wire it in**: connect an upstream node (file / image / video / audio / save) to a terminal; when
   this step starts running, whatever is wired in **counts as delivered** for that entry (its terminal
   disappears). You do not have to confirm it by hand.
2. **Upload one by one**: press **⬆ Upload** on a terminal and pick **the file that terminal asks
   for** — the file name must match the terminal label. A mismatch is flagged in red but the file is
   **still accepted** (delivery is a human act; the system warns, it does not block). Revoke and
   re-upload if you picked wrong. Files are copied into the fixed folder above; your originals are
   untouched.

The format / size note behaves the same way: writing `.md only · ≤ 2 MB` flags a `.txt` or an
oversized file, but never turns you away.

Checklist entries come in four kinds — **file / text / choice / media** — each required or optional.
Once every required entry is delivered the node only shows **ready**; the step is released when **you**
press “确认交付完成” on the strip card. The system never decides that delivery is complete for you.
**Revoke** only clears the delivered mark and brings the terminal back — files in the delivery folder
are never deleted.

Re-running the same step is a **new round**: the list is re-injected, every terminal comes back and you
deliver again (last round's files stay in the delivery folder for review).


## About the uid

A uid looks like `lt<8 base36>-<step short name>`. It is the identity of that human step: the folder
name, the manifest and the strip card are all matched through it. **Do not edit it** — downstream
steps would stop finding the delivery.

## Can I delete it?

- Yes. If you delete it, the step is marked “node needs rebuilding”, and the system creates it again
  the next time that step is reached (same uid, same folder).
- **No duplication**: right-click copy, Ctrl+C / Ctrl+D and agent graph editing all refuse this kind.
  It is the single landing spot for one step; a second copy would break the accounting.
- Deleting a task or a run never removes delivery folders: they are only reported as orphaned in
  “交付目录体检”.

## Why there is no palette entry

You will not find this kind in the node list, the context menu, the wire drop targets or the tool
library — by design, only the long-task system creates it. To start using it: drag the thin line
above the canvas down, create a long-running task, add a **human** step with mode `deliver`, then
press **Enable & bind**.
