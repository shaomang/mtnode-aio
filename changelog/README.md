## 写作规范

1. **只写用户能感知的变化**：允许产品 / 功能名（画布、开发节点、素材库、@ 引用…）；禁止文件名、函数名、类名、接口与协议名、性能数字，以及「重构 / 解耦 / 抽象」这类工程词。
2. **最多两层条目**：版本标题 → 分类（新增 / 改进 / 修复）→ 条目；某个分类没有内容就整块省略。
3. **文件形状**：`changelog/v<版本>.md`，H1 是 `v<版本>（YYYY-MM-DD）`，紧跟一行摘要，再按分类列条目。
4. **条目写法**：一句话、动宾结构，尽量不超过 40 字，句末不加句号；一条一件事，不合并成一句长话。
5. **摘要**：说清这一版最值得说的一件事，不重复版本号。
6. **「修复」要写现象**：如「切换画布后节点参数丢失」，不要写「修复若干问题」。
7. **确实没有用户可见变化**：摘要写「内部维护与稳定性」，正文写一行「本版以内部维护为主，无用户可见变化。」，不要为凑数编条目。
8. **版本号与日期**：版本号取根 `version` 文件；日期取该版发布提交的日期（`dist/latest.yml` 的 `releaseDate` 可作参考）。
9. **每版必写，且由发版链强制**：`scripts/release.mjs` 在打包前校验 `changelog/v<当前版本>.md` 存在且至少有一条条目（或写了「无用户可见变化」），缺失即中断发版。
10. **取材**：由 Agent 会话在用户授权下读**只读** git 历史（相邻发布提交的差异 + 界面词条 + `guides/` 与 `docs/` 交付说明）起草，人工润色后提交；写完同步本文件的版本索引表。

```md
- 用户遇到过的现象不再出现
```
