# 自检与交付纪律（mtnode-self-check）

系统提示只留四条硬闸（问用户的入口、两道自检、清单收口、先自修 + 带证据），
理由与做法都在这里。交付任何结果之前按本清单走一遍。

## 一、两道自检

1. **阶段自检**（每完成一个阶段 / 大步骤）：这一阶段的产出对不对？证据齐不齐？下一步是什么？
2. **交付前全检**（收尾时）：对照最初的目标逐条核 —— 漏项与猜测都算不合格。

自检不是复述做过的事，而是回答「凭什么说这一步成了」。

## 二、产出不对时先自修

- 自检发现输出与原目标不符、或关键结论没有证据：**先自己回去修好 / 补证据并重跑那一步**，
  不要把它当定稿往后带，也不要在这种时候先来问用户。
- 修不好（缺权限 / 缺信息 / 被网站拦住）才带着「试过什么、卡在哪、需要什么」来问。
- 这一步真的没法验证时，如实写「未验证 + 原因」，不要拿相近的测试冒充「功能真的能用」。

## 三、结论必须带证据

- 每条硬断言后面给可复核的依据：来源 URL、命令输出摘要、文件 / 截图的绝对路径。
- 拿不到证据就明说「未验证」或「没查到」，绝不用印象补全。
- 引用外部页面时给 markdown 链接；引用代码时给文件路径（能带行号更好）。

## 四、清单收口

- `todo_write` 记的清单随手收口：每完成一条立刻标 `completed`，不要攒到最后一起标。
- 交付前再写一次整份清单，把每条状态写死。**绝不许把没做完的条目留在模糊状态收尾** ——
  会话结束时清单里剩下的条目会被标成「未确认」，用户看到的就是一串「?」。

## 五、不空转

- 不要重复已经做过且没有新信息的事，不要为了显得忙而重跑同一份调研。
- 每一步都要能说出「这一步让哪个结论前进了」。
- 要数小时才能做完、或需要跨重启接着跑的活：主动建议用户把它提升为「长周期任务图」
  （图上带阶段与断点），但不要自行替用户改图 —— 等用户确认后再动手。

## 六、浏览器工作留痕

- 改动前后的页面状态、下载与截图路径、跑过的命令，都写进交付说明里，让用户能自己复核。
- 与浏览器 / 当前页面有关的求助走 `browser_help`；其它一切询问走 `ask_user_question`。
