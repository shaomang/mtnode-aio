# 全仓体检（一次出报告）

像一个刚接手这个仓库、并且会在它挂掉时被叫起来的资深工程师那样体检。优先级：**正确 → 安全 → 扛得住负载 → 有测试 → 够快 → 够省**。省也要管：多出来的每一行以后都要有人读、有人测、有人修。用户要的是报告，就给完整的。

准则本体在同库主技能 `ponytail`；本技能只负责「整仓一次性查得严」，不动手改码。

## 何时用

- 用户说「体检一下这个仓库 / 这个包 / 这个目录」「review the whole repo」「找找有多少赘肉」「什么能删」「技术债有多重」。
- 刚接手一个仓库、要给出「先修什么」的排序时。
- 不适用：只评审一次具体改动 → `ponytail-review`；只列 `shortcut:` 标记 → `ponytail-debt`；要动手改 → `ponytail`。
- **硬规则：一次性只读。** 不改码、不提交、不改配置；报告里给「最小修法」，等用户点单。

## 核心原则

1. **先摸清，再深入**：入口、部署、依赖、测试都不看就报问题的体检没有价值。
2. **必须写清负载假定**：同一个实现，一个人跑脚本没事、多用户并发就挂。报告开头一句话交代你按什么规模判断的，以及依据（README / 部署配置 / 启动脚本）。
3. **按后果排序，不按文件顺序**：一个大仓不要逐文件读，去错误代价最高的地方深挖，并写明哪些部分没读。
4. **每条发现都要有具体情形**：什么输入 / 什么状况 → 什么错结果。给不出情形就不是发现。
5. **最多 20 条**：超出的宁可砍掉最轻的，也要在收尾写清「还剩下多少条没列」。报告要能被执行，不是要一网打尽。
6. **`shortcut:` 里写清上限的是决定，不是发现** —— 除非期望负载已经越过那条上限。
7. **没有风格口味、没有「可以考虑」、没有含糊的担忧。**

## 工作流

### 第 1 步：摸图

- 体检用户点了名的范围（目录、包、整个仓）。没点名就整仓。
- 读 README、部署与构建配置、依赖清单、入口（main、路由、handler、定时任务、CLI 命令）与测试。
- **定负载**：一个人跑脚本，还是很多用户与进程并发？依据写进报告。判断不了的写「未能确定负载，按 <X> 假定并已标注风险」。
- 顺着主流程端到端走一遍：从哪进、存了什么、从哪出。这些路径要读完：用户输入、钱、鉴权、写盘、后台任务、跨进程共享的东西。
- 大仓：只在「错一次最贵」的地方深挖，并明确列出没读的部分。

### 第 2 步：只找这六类

1. **缺陷**：结果错、崩溃、漏边界（空、零、最后一项、四舍五入、时区）、调用方与函数实际返回值不一致、同一条规则在两个地方写法不同。
2. **风险**：安全漏洞（注入、弱随机、代码里的密钥、外部输入不校验）、数据丢失（错误被吞、写入顺序错、没有事务）。
3. **规模**：单用户没事、多用户就错：`check-then-write` 竞态、每个进程都做一遍同样的活、只增不减的内存或列表、每条一次查询、大输入上的 O(n²)、本该共享却是进程内的状态。
4. **缺测试**：有风险的逻辑（分支、解析器、钱、安全、写盘）没有「坏了会红」的测试。一条好测试就够，不看覆盖率。
5. **速度**：慢一个数量级是问题；热循环里的小优化只是建议。
6. **省**：本不该存在或该更小的代码 ——
   - **删**：死代码、没人用的选项 / 开关 / 配置、猜想中的功能
   - **复用**：两个 helper 干同一件事（留一个，写出路径）
   - **标准库 / 平台**：原生就能干；或者一个依赖干的事几行代码 / 平台本身就能干
   - **yagni**：只有一个实现的接口、只有一个产品的工厂、只转发调用的包装层
   - **合并**：必须一起改的近似副本
   - **拆分**：一个函数或类干几件不相关的事 —— 按职责拆，绝不按行数拆

### 第 3 步：落笔前先自证

- 每条都要有具体情形；没情形就不写。
- 判「没人用」之前，全树 grep：测试、fixture、配置、字符串引用、动态引用都要查。
- 修法给最小可用的，优先删代码；不引入新层、新框架、没人要的配置。
- 排序复核：如果一条「可选」排在「必须改」前面，说明分级错了。
- **数量复核**：超过 20 条就按后果砍到 20，砍掉的条数写进收尾。

### 第 4 步：按固定格式出报告

开头两句 + 负载假定 → 三级分组 + 四段式发现 → 三行固定收尾（模板见下节）。

## 关键参数与模板

### 开头

```
这个仓库在做什么：<两句话>
负载假定：<一个人跑脚本 / 多用户多进程并发>，依据：<README 某段 / 部署配置某文件>
```

### 三级分组（从重到轻，空组跳过）

| 组 | 装什么 |
| --- | --- |
| **必须改** | 缺陷、安全、数据丢失、在期望负载下会挂 |
| **应当改** | 有风险却无测试、真的慢、重复、一个函数混了几件事、本不该存在的代码 |
| **可选** | 小提速、更短的写法 |

### 四段式发现（每条必须四段，缺一段算没写完）

编号**跨组连续**，用户才能说「修 2 和 5」。**总数上限 20 条。**

```
2. **订单落在错误的那一天**（`billing/close_day.py:L40-52`）
   - **这是什么**：这个任务每天零点关账，把当天订单全部结账。
   - **问题**：它从服务器时钟取「今天」，而服务器跑在 UTC；柏林时间 00:30 下的单会被结到前一天。
   - **最小修法**：按店铺时区算一次日期 `datetime.now(ZoneInfo("Europe/Berlin")).date()`。一行，别的都不动。
   - **不修会怎样**：晚间的单日期全错，财务只能手工改。
```

### 收尾三行

```
结论：<健康 / 先修 1 和 3 / …>（一行）
省：-<N> 行、-<M> 个依赖是可行的。（有「省」类发现时才写）
没查的：<没读到的部分、跑不起来的检查>；另有 <K> 条更小的问题未列出。（K>0 时必须写）
```

一条都没发现：

```
这个仓库在做什么：<两句>
负载假定：<…>

健康，没有要修的。
查了：<入口、依赖、写盘路径、测试…一行>
```

## 常见坑

- **不写负载假定就下结论**：「这个没加锁有问题」在单人脚本里是误报；给了假定，结论才可复核 —— 这是本技能与随手点评的分界线。
- **想穷尽**：几百条发现没人会修。20 条上限是纪律，不是建议；砍掉的必须报数。
- **逐文件读小问题**：先沿贵路径走，大小问题分得清再说。
- **把 `shortcut:` 当债**：写清上限与升级条件的标记是决定，重复报一遍会稀释报告。
- **不报没读到的范围**：没读就说没读，别让用户以为整仓都验过了。
- **顺手改码**：本技能一次性只读。改了就变成另一件事，必须另外问过用户。
- **在体检里顺手评审某一笔改动 / 列 debt 台账**：那是 `ponytail-review` / `ponytail-debt`，各管一段。
- **只报「省」不报「难」**：只列可删的东西最讨好、最没用；必须先报会算错、会丢数据、会挂。
