# 改动评审（只出报告不改码）

像那个改动上线后半夜被叫起来的资深工程师一样评审。优先级：**正确 → 安全 → 扛得住负载 → 有测试 → 够快 → 够省**。省也要管：多出来的每一行以后都要有人读、有人测、有人修。用户要的是报告，就给完整的。

准则本体在同库主技能 `ponytail`；本技能只负责「查得严」，不动手改码。

## 何时用

- 用户说「评审一下」「帮我看看这个改动」「code review」「review 这个 PR / 这个分支」「review 上一笔提交」「这段是不是过度设计」。
- 一个改动要合进来、要发版、或作者本人不确定是否合规时。
- 不适用：要动手改 → `ponytail`；整仓体检 → `ponytail-audit`；`shortcut:` 标记台账 → `ponytail-debt`。
- **硬规则：本技能只读。** 一行也不许改。发现要改的东西写进报告的「最小修法」，等用户点单再动手（那时切到 `ponytail`）。

## 核心原则

1. **评审对象 = 改动 + 它碰到的代码**，不是 diff 本身。改签名、改返回值、改行为都可能弄坏没被改到的调用方。
2. **每条发现都要有具体情形**：谁输入什么 → 得到什么错结果。给不出情形就不是发现。
3. **分级只看后果，不看作者心情**：会算错 / 会丢数据 / 会挂 = 必须改。
4. **修法取最小改动**，优先能删代码的那种；不引入新层、新框架、没人要的配置。
5. **`shortcut:` 里写清上限的捷径是决定，不是发现** —— 除非当前负载已经越过那条上限。
6. **没有风格口味、没有「可以考虑一下」、没有含糊的担忧。** 报告短而硬，比长而软有用。
7. **报告要给全**：用户要的就是这份报告，不要因为「怕说太多」而省掉应当改里的条目。

## 工作流

### 第 1 步：先弄清评审对象

- 用户点了名就评审它：未提交 / 已暂存的改动、某个分支、PR 链接、某几个文件。没点名：未提交的改动；没有未提交改动就评审上一笔提交。
- 读 diff，再读它碰到的代码：每个被改函数的调用方、它调用的函数、相关测试、README。
- 顺真实数据流走一遍：从哪进、存了什么、从哪出。
- 改签名 / 改返回值 / 改行为时 **grep 全部调用方**（含测试、fixture、配置、动态引用）。
- 找出仓库里的期望负载（README、部署配置）：一个人跑脚本，还是很多用户与进程并发。按这个规模判断，并在报告开头写明**假定的是哪种负载**。

### 第 2 步：只找这六类

1. **缺陷**：结果错、崩溃、漏边界（空、零、最后一项、四舍五入、时区）、被改坏的调用方、只在一个调用方打补丁而共享函数仍然坏着。
2. **风险**：安全漏洞（注入、弱随机、密钥、外部输入不校验）、数据丢失（错误被吞、写入顺序错、没有事务）。
3. **规模**：单用户没事、多用户就错：`check-then-write` 竞态、每个进程都做一遍同样的活、只增不减的内存或列表、每条一次查询、大输入上的 O(n²)、本该共享却是进程内的状态。
4. **缺测试**：有风险的新逻辑（分支、解析器、钱、安全、写盘、bug 修复）没有「坏了会红」的测试。一条好测试就够，不看覆盖率。
5. **速度**：慢一个数量级是问题；热循环里的小优化只是建议。
6. **省**：本不该存在或该更小的代码 ——
   - **删**：死代码、没人设的选项、猜想中的功能
   - **复用**：仓库已有这个 helper（写出路径）
   - **标准库 / 平台**：原生就能干，却为一个函数引了依赖
   - **yagni**：只有一个实现的抽象、没人设的配置
   - **合并**：必须一起改的近似副本
   - **拆分**：一个函数干几件不相关的事 —— 按职责拆，绝不按行数拆，也不许拆出「只为让函数变短」的 helper

### 第 3 步：落笔前先自证

- 复核那几行：调用方真的存在？那个值真的可能为空？那段代码真的没人用？（判「没人用」必须全树 grep，含测试、fixture、配置与字符串引用。）
- 每条都要有具体情形；没情形就不写。
- 修法给最小可用的，优先删代码。
- 写完回头过一遍：这一条是「后果」还是「口味」？是口味就删掉。

### 第 4 步：按固定格式出报告

先两句话「这个改动在做什么」，再三级分组 + 四段式发现，末尾三行固定收尾（模板见下节）。报告里不出现「我改了」「顺手修了」——本技能不改码。

## 关键参数与模板

### 开头

```
这个改动在做什么：<两句话；读者可能从没见过这段代码>
负载假定：<一个人跑脚本 / 多用户多进程并发，写清依据（README、部署配置）>
```

### 三级分组（空组直接跳过）

| 组 | 装什么 |
| --- | --- |
| **必须改** | 缺陷、安全、数据丢失、在期望负载下会挂 |
| **应当改** | 有风险却无测试、真的慢、重复、一个函数混了几件事、本不该存在的代码 |
| **可选** | 小提速、更短的写法 |

### 四段式发现（每条必须四段，缺一段算没写完）

编号**跨组连续**，用户才能说「修 2 和 5」。

```
3. **订单落在错误的那一天**（`billing/close_day.py:L40-52`）
   - **这是什么**：这个任务每天零点关账，把当天订单全部结账。
   - **问题**：它从服务器时钟取「今天」，而服务器跑在 UTC；柏林时间 00:30 下的单会被结到前一天。
   - **最小修法**：按店铺时区算一次日期 `datetime.now(ZoneInfo("Europe/Berlin")).date()`。一行，别的都不动。
   - **不修会怎样**：晚间的单日期全错，财务只能手工改。
```

- 位置写 `文件:行号` 或 `文件:行号-行号`；每条一到两句话，别写成小作文。
- 「最小修法」里如果要写代码，就给可以直接粘的那一行，不要给「建议重构一下」。

### 收尾三行

```
结论：可以发。| 先修 1 和 3。
省：-<N> 行是可行的。（有「省」类发现时才写）
没查的：<重要但确实查不清的那一条>（没有就不写这行）
```

一条都没发现：

```
这个改动在做什么：<两句>
负载假定：<…>

看起来可以发。
查了：<diff、调用方、测试、README…一行>
```

## 常见坑

- **把 diff 当全部**：不读调用方的评审最容易漏掉「改签名打断调用方」这类必挂问题。
- **没有具体情形的发现**：「这里可能有问题」等于没写，用户还得自己判断一遍。
- **把 `shortcut:` 当债**：注释里写清上限与升级条件是决定，重复报一遍只会让用户关掉评审。
- **风格口味混进必须改**：命名、缩进、顺序偏好不进报告。
- **顺手改了代码**：本技能只读。改了就不是评审，是另一件事，必须另外问过用户。
- **不给「不修会怎样」**：没有后果这一句，用户无法排序，整份报告就失去价值。
- **不写负载假定**：同一份并发代码，单用户脚本没事、多进程就挂；不说明假定，结论无从复核。
- **在评审里做全仓体检或技术债台账**：那是 `ponytail-audit` / `ponytail-debt`，混着做会让各自的触发条件互相稀释。
