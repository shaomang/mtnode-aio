# 开发会话收尾回写：目标语义与最小改动面（决策定稿）

> 性质：并行计划中的「语义敲定」子任务，交付决策 + 最小改动规格。
> 定稿口径由用户在确认问答中选定 = **方案 B 原话**，并补充一条自定义澄清。
> 本文为唯一决策依据；不直接改动共享源文件（它们在并行子任务中正在被同时修改，动刀会冲突）。

## 一、定稿语义

默认（A/B 之外补充澄清）**开发会话不修改节点标题**。也就是说节点 title 由用户在画布上
维护，会话侧绝不通过收尾回写把 title 覆盖成会话主题 / 模块概述摘要。

收尾只允许回写三样，且**均不改 title**：

1. **note** —— 只允许按两段式规范回写**模块两段式概述**（【功能】面向非技术 + 【实现】
   面向技术梗概）。**禁止**用「会话主题 / 聊天总结 / 实施摘要」整体覆盖 note。
2. **devStatus** —— 保留原流转（dev 开始时 `wip`，收尾按完成度落到 `done`）。
   **不得一刀切禁用**，否则功能块会永远停在 `wip`，与既有开发工作流状态跟踪冲突。
3. **devFiles** —— 保留；收尾仍用 `mtnode_canvas_edit` 的 devFiles 补丁回写本模块真实核心文件。

会话标题的同步仍沿用既有逻辑：**节点改名 → 其名下的开发 / 细化会话标题跟随**
（`syncDevSessionTitles`，前缀「开发 · / 细化 · 」保留、只换后半段模块名），
这是「会话标题跟随节点标题」的唯一合法路径，不受本决策影响。

## 二、代码现状核实（勘察结论）

- 开发 / 细化任务书契约（`renderer/app.js` 的 `devNodeContractText`，行 ~26347 收尾指令）与
  只读问询契约（`renderer/app-devnode.js` `devAskContractText`）的**收尾指令从未要求改节点 title**，
  只要求回写 note / devStatus / devFiles。
- 全局助手人格里那条「画布修改只限收尾回写本节点（note / devStatus / devFiles）」也**不含 title**。
- 节点 title 的自动/回写逻辑只存在于 **agent_task 节点 ↔ 会话**的
  `syncAgentTaskToSession` / `syncAgentTaskFromSession`（app.js 行 ~26834 / ~26876），
  以及**用户改名 → 会话跟随**的 `syncDevSessionTitles`（app.js 行 ~26394）。
  这两者都**不属于** dev 功能块的收尾回写，不纳入本改动。
- 结论：本决策要落地的是「显式申明 + 防未来回归」，而不是删一段已经在写 title 的代码 ——
  现网没有那样一段收尾代码需要移除。

## 三、最小改动面（待并行落地的 PR 规格）

仅在**任务书契约文本**（提示词真源层）加一句显式约束 + 注释，不改画布补丁逻辑、不改 devStatus
/ devFiles 的执行代码。候选句（追加在现有收尾指令之后）：

> 收尾只回写本节点的两段式概述（note，按【功能】/【实现】规范）、状态（devStatus）与核心文件
> 列表（devFiles）。**不要修改本节点的标题（title）**，也不要用会话主题 / 实施总结覆盖 note。

需要落点的文件与行（均为契约文本，多语言键随 i18n 一并维护）：

| 文件 | 位置 | 说明 |
| --- | --- | --- |
| `renderer/app.js` | `devNodeContractText` 收尾指令（行 ~26347，i18n 键 ~i18n.js:3831） | 「开发」任务书契约 |
| `renderer/app.js` | 拷问段收尾句（行 ~26304，i18n 键 ~i18n.js:3630） | 拷问模式结束后的回写描述 |
| `renderer/app-devnode.js` | 开发建议→开发收尾句（行 ~726，i18n 键 ~i18n.js:3829） | 建议弹窗「开发」入口契约 |
| `renderer/app-assist.js` | 助手画布批准句（行 ~4758，中文硬编码） | noCanvasRead 档人格，纯中文无 i18n |
| `renderer/i18n.js` | 对应上表各键 | 中英双语同步改 |

注释要点（写进 PR 与上述行附近代码注释，避免后人误砍 devStatus）：

- devStatus 流转 = 工作流状态跟踪的一部分，砍掉会让功能块永远 `wip`；
  本改动只约束 **title / note**，不触碰 devStatus / devFiles。
- note 的两段式概述是模块的「设计文档」，会话总结是对话噪声，二者必须区分；
  只许前者、禁后者。

## 四、取舍与防回归

- **为什么不做方案 A（收尾完全不写回节点）**：收尾回写 note 两段式概述、devStatus 落到 done、
  devFiles 是真实验收产物。一刀切关闭会让功能块状态跟踪断链（永远 wip、核心文件列表停在自动
  兜底甚至空表），与既有「开发 / 细化」工作流冲突。故选 **B**。
- **不改画布补丁/执行逻辑**：canvas-plugin 的 update 已支持按节点 id 定位 + setTitle；本决策不新增
  也不删除任何补丁能力，只在「会话该不该动 title」这一层做语义收紧。
- 未来若有人给开发会话契约加「把主题写进节点」的指令，应回到本文档确认口径，防止回归。
