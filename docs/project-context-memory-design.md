# 项目上下文与记忆体系设计

> 状态：v1 设计
> 目标：让「建议 / 问询」等只读调研角色能**基于项目真实情况**给出建议，而不是每次从零猜。
> 范围：上下文分层模型、记忆读写流程、注入策略、项目级与角色级的隔离/共享边界。
> 不涉及：模型选型、画布 UI 细节、数据库节点的事实查询实现（另见 `docs/dev-node-design.md`、技能 `mtnode-db-facts`）。

---

## 1. 问题与设计原则

角色要「懂项目」，缺的不是模型能力，而是**稳定的项目事实**与**可控的上下文预算**。现状痛点：

- 每次建议都要重新扫描代码库 / 重新读一遍历史结论，慢且不稳定；
- 角色之间的历史结论互不可见，同一问题反复讨论、结论互相矛盾；
- 把整个项目塞进上下文既超预算又降质（噪声、串味），而只给一句标题又没依据。

四条原则：

1. **事实与推断分离**：代码 / 配置 / 数据库里能查证的是「事实」，角色写的判断是「记忆」。事实不进记忆库，每次按需重取（避免过期）。
2. **分层归属**：每一条上下文都有明确的**归属层级**与**可见性**，注入时按层级装配，而不是一个大字符串。
3. **按需检索优先**：默认不全量注入，用检索 + 排序 + 压缩把预算花在最相关的条目上；只有小体量、高价值、必须全见的内容才全量。
4. **写入门槛高于读取**：记忆写入要经过提炼、去重、冲突检测才落盘；宁可少写，不可污染。

## 2. 上下文分层模型（L0–L5）

| 层 | 名称 | 内容 | 归属 / 可见性 | 生命周期 | 存储形态 | 典型体量 |
|---|---|---|---|---|---|---|
| **L0** | 系统与能力层 | 角色系统提示、工具说明、行为纪律、输出格式 | 全局，所有角色相同 | 永久（随版本） | 内置代码 | 2–6k tok |
| **L1** | 项目档案层 | 目标、阶段、约束、资源（见 §3） | 项目级共享，全部角色只读 | 项目生命周期，人工/半自动维护 | `PROJECT.md`（结构化 YAML 头 + 正文） | 0.5–2k tok |
| **L2** | 项目共享记忆 | 已确认的结论、决策、约定、风险、术语表 | 项目级共享，全部角色可读写 | 长期，可归档/失效 | `memory/project/*.md` + 索引 | 按需 1–4k tok |
| **L3** | 角色私有记忆 | 该角色的偏好、历史判断、未验证假设、被否决方案 | 仅该角色可见（严格隔离） | 长期 | `memory/roles/<roleId>/*.md` | 按需 0.5–2k tok |
| **L4** | 会话工作记忆 | 本次会话的目标、已读文件、中间结论、待办 | 会话内共享（同会话的多轮） | 会话结束即归档/丢弃 | 会话 JSONL（现有 dsh 会话） | 滚动窗口 |
| **L5** | 即时任务层 | 本次运行的任务书、@引用节点、显式指定的文件片段 | 本次运行 | 单次运行 | 运行时装配 | 由预算决定 |

装配顺序（后写的更靠后、优先级更高）：`L0 → L1 → (L2 检索结果) → (L3 检索结果) → L4 摘要 → L5 任务书`。

要点：

- **L2 与 L3 同格式、不同命名空间**，读写走同一套 API，靠 `scope` 区分；L3 在检索与注入时只取当前 `roleId` 的命名空间。
- **L4 是「会话」不是「记忆」**：会话结束只把**通过写入流程**的条目晋升到 L2/L3，其余丢弃。禁止把整段会话历史直接当记忆注入。
- **L1 与 L2 的边界**：档案是「项目的客观状态」（阶段、约束、资源），共享记忆是「角色达成的结论」。约束类事实放 L1，判断类结论放 L2。

## 3. 项目档案（L1）结构

`PROJECT.md`：YAML 头（机器读）+ 正文（人读），单一真源，改动记时间戳。

```yaml
project: mtnode-ai-orchestrator
root: E:\dev\tools\pipeline-console
goal:
  summary: 桌面端 AI 工作流编排器
  nonGoals: [云端协作, 移动端]
stage:
  phase: 迭代中          # 立项 / 迭代中 / 稳定 / 维护
  milestone: v1.1.28
  deadline: null
constraints:
  tech: [Electron 39, 无前端框架, Node >= 22.19]
  process: [根目录新模块必须进 build.json files]
  forbidden: [改 node_modules, 手改 version 字段]
resources:
  entryDocs: [AGENTS.md, dsh/DESIGN.md]
  keyPaths: [main.js, renderer/, dsh/gateway/]
  owners: [{area: 网关, who: ""}]
updatedAt: 2026-02-01
```

- **人工确认优先**：档案的 `goal / stage / constraints` 由用户或「建议」运行提议、用户确认后写入；Agent 不得静默改写。
- **可推导的用工具现查**：`root`、`keyPaths` 里的文件列表等能扫描得到的内容**不重复存**，只存指针（`keyPaths`）与规则（`forbidden`）。
- 档案缺失时角色应显式声明「项目档案缺失」，而不是自行编造目标。

## 4. 记忆条目与读写流程

### 4.1 条目 schema

```yaml
id: mem-proj-0007
scope: project | role
roleId: architect            # scope=role 时必填
type: decision | convention | risk | term | openQuestion | rejected
title: 根目录主进程新模块必须进 build.json
body: 否则打包后 Cannot find module './xxx.js'。
evidence: [AGENTS.md#打包白名单, docs/reports/...]   # 可核验来源
tags: [build, packaging]
confidence: high | medium | low
status: active | superseded | archived
supersedes: mem-proj-0003
createdAt: 2026-01-12
updatedAt: 2026-01-20
```

规则：`evidence` 必填（文件路径 + 行/章节，或数据库 `[记录id · 标题]`）；无来源的条目只能是 `confidence: low` 且归 L3。

### 4.2 写入流程（提炼 → 去重 → 冲突 → 落盘 → 索引）

1. **触发**：仅在这些时机写入，不实时记录每一步思考——
   - 会话结束前的显式「沉淀」步骤；
   - 角色产出的结论被用户确认；
   - 检测到与既有记忆矛盾的强证据。
2. **提炼**：把会话中的结论压成「一句判断 + 依据」，丢弃过程与闲聊。
3. **分类**：`type` + `scope`。项目级客观约定 → L2；角色主观判断/未验证假设 → L3。
4. **去重**：与索引中同 `tags`/`title` 的条目做相似度比对，命中则合并 `evidence`、更新时间，不新增。
5. **冲突检测**：与同主题 `active` 条目矛盾时**不覆盖**——新条目写入并 `supersedes` 旧条目（旧条目置 `superseded`），冲突在建议中显式提示「存在两种结论，依据如下」。
6. **落盘**：`memory/project/<type>/<id>.md` 或 `memory/roles/<roleId>/<type>/<id>.md`，一文件一条目，YAML 头 + 正文。
7. **索引**：追加到 `memory/index.jsonl`（id、scope、roleId、type、tags、title、status、updatedAt、embedding 可选）。索引是检索的唯一入口，禁止全目录扫描。

**遗忘与衰减**：`superseded` / `archived` 不注入；`confidence: low` 且 30 天未被引用降级归档；被代码证伪的事实类条目直接删除（事实应重新从源头取）。

### 4.3 读取流程（检索 → 排序 → 压缩 → 装配）

1. **构造查询**：由 L5 任务书 + 当前开发节点 `note` + 相关文件路径组成查询串。
2. **候选召回**：索引按 (a) 标签/路径匹配、(b) 关键词、(c) 可选向量相似度召回 top-K（K≈20）。
3. **排序打分**：
   `score = 相关度 × 0.5 + 层级权重(项目级 1.0 / 角色私有 0.8) × 0.2 + 新鲜度 × 0.2 + confidence × 0.1`，
   `superseded/archived` 直接过滤。
4. **压缩**：命中条目按 `title + 一句话 body + evidence 指针` 注入；正文长条目截断到预算上限，完整内容留在文件里供角色按需 `read`。
5. **装配**：按 §2 顺序拼装，带层标记（`## 项目档案` / `## 项目记忆（检索 7 条）` / `## 你的历史判断`），让角色知道每条的依据等级。

## 5. 注入策略：全量 vs 检索增强

### 5.1 决策矩阵

| 内容 | 体量 | 策略 | 理由 |
|---|---|---|---|
| L0 系统提示、工具说明 | 固定 2–6k | **全量** | 每次必须一致 |
| L1 项目档案 | ≤2k | **全量** | 全角色共同前提，且经人工裁剪 |
| 项目约定 / 术语表（`convention`/`term`） | 小 | **全量**（默认全部 active） | 少量、高频、错一条就错一片 |
| 项目结论 / 决策 / 风险（`decision`/`risk`） | 增长 | **检索增强** | 量大且与任务局部相关 |
| 角色私有记忆 | 中 | **检索增强**（只查本角色命名空间） | 隔离 + 控预算 |
| 代码 / 配置 / 数据库事实 | 大 | **永不缓存注入**，按需 `read` / 工具现查 | 易过期 |
| 会话历史 | 大 | **压缩摘要**（滚动窗口 + 结论列表） | 避免噪声与串味 |

**经验阈值**：单层检索结果超过 ~4k tok 时，只保留 top-8 并给出「另有 N 条相关记忆，可展开」的提示；档案超过 ~2k tok 说明该拆分了（正文移入 L2）。

### 5.2 预算分配（以 16k 上下文为例）

| 层 | 预算 | 说明 |
|---|---|---|
| L0 | 4k | 固定 |
| L1 | 1.5k | 档案 + 约定/术语全量 |
| L2 | 3k | 检索 top-8，压缩后 |
| L3 | 1.5k | 检索 top-5，仅本角色 |
| L4 | 2k | 会话摘要 |
| L5 | 3k | 任务书 + 指定片段 |
| 余量 | 1k | 工具返回预留 |

超预算时的裁剪顺序：**L3 → L2（低分条目）→ L4（更早的轮次）→ L5 的附加片段**；L0 与 L1 不裁剪（裁了角色就失去前提）。

### 5.3 项目文档 / 资料接入

- **登记而非拷贝**：外部资料（设计文档、接口说明、Excel 等）在档案 `resources.entryDocs` 或 L2 条目里登记**路径 + 用途**，不把正文塞进记忆。
- **接入优先级**：`AGENTS.md` 等共识文件 > 档案 `keyPaths` 内文件 > 检索命中的文档片段。
- **大文件**：先取目录 / 章节标题，再由角色按需 `read` 具体段落；禁止整篇注入。
- **资料更新**：以文件 mtime 为失效信号，记忆条目引用资料时记录 `evidence` 版本（章节/行号），资料变更后引用条目需复核。

## 6. 隔离与共享边界（防串味 / 防泄漏）

### 6.1 共享（可跨角色见）

- L0 系统与工具能力；
- L1 项目档案（只读）；
- L2 项目共享记忆：客观结论、已被用户确认的决策、项目约定、术语、风险；
- L4 同一会话内的工作记忆。

### 6.2 隔离（角色私有）

- L3 角色私有记忆：该角色的偏好、风格、历史判断、未验证假设、被否决方案；
- 其它角色的 L3 **不可见、不可检索、不可引用**；角色输出中不得出现「另一角色认为…」除非该结论已晋升到 L2。

### 6.3 边界规则

| 场景 | 规则 |
|---|---|
| 角色想把自己的判断给别的角色看 | 必须**晋升**：经用户确认 → 写为 L2 条目（带 `evidence` 与 `roleId` 来源），原 L3 条目置 `superseded` |
| 角色想引用别人的结论 | 只能引用 L2；引用时带上条目 `id` 与依据 |
| 同一主题不同角色结论冲突 | 两者都可写 L3；L2 只保留「已裁决」的结论，冲突双方以 `openQuestion` 记录 |
| 敏感信息（密钥、个人数据、客户资料） | 一律不入记忆库；`evidence` 只写指针，正文脱敏。写入前做一次敏感词/凭据格式扫描 |
| 跨项目复用 | 默认禁止。记忆与档案绑定 `project.root`，切换项目即切换命名空间；跨项目迁移需显式导出/导入 |

### 6.4 串味的三个来源与对策

1. **把会话历史整段当记忆** → 只允许经 §4.2 写入流程的条目进入 L2/L3。
2. **检索时跨命名空间** → 检索 API 强制 `scope` 参数；L3 查询自动注入 `roleId` 过滤，缺少 `roleId` 直接报错。
3. **角色提示里混入通用「人格」而非项目事实** → L0 只写角色职责与输出格式，项目相关信息一律来自 L1/L2，禁止在系统提示里硬编码项目结论。

## 7. 落盘布局与能力映射

```
<项目根>/
├─ PROJECT.md                      # L1 项目档案（单一真源）
├─ AGENTS.md                       # 既有共识文件（L1 的 entryDocs）
└─ .mtnode/memory/                 # 记忆库（默认不进版本控制，可配置）
   ├─ index.jsonl                  # 检索索引
   ├─ project/<type>/<id>.md       # L2 项目共享记忆
   └─ roles/<roleId>/<type>/<id>.md# L3 角色私有记忆
```

与现有能力的映射（不新增机制，复用）：

| 设计要素 | 落地方式 |
|---|---|
| L1 / L2 / L3 存储 | 工作区文件（Markdown + YAML 头），可用现有 `read` / `write` / `edit` 工具读写 |
| 索引与检索 | `index.jsonl` + 关键词/标签打分；向量检索作为可选增强，不阻塞 v1 |
| 角色运行 | 「建议 / 问询」只读运行：装配 L0–L5 后执行，运行结束走沉淀流程；角色人设走 `persona_host` 分节（`renderer/app-team.js` 装配），工具白名单 / 审批档复用 `agentToolPresets` / `permissionPreset`，模型复用 `provider-model-effort` |
| 咨询编排 | 回合制多 run（一次发言 = 一次 dsh run），状态进 `S.config.team`，产出落项目工作区文件；**不新增主进程 `consultation-engine.js`** |
| 结论沉淀 | 渲染层 `renderer/app-team.js` 写 `decisions/*.md` + 更新 `index.jsonl`；**不新增主进程 `decision-store.js`** |
| 事实核验 | 数据库相关走 `mtnode_db`（`mtnode-db-facts` 纪律）；代码事实走 `read` / `glob` / `grep` |
| 会话工作记忆 | 现有 dsh 会话 JSONL；结束时生成摘要，结论经写入流程晋升 |

> **落地口径**：记忆、决策、咨询编排全部落在渲染层 `renderer/app-team.js` + `S.config.team` + 项目工作区文件，**不新增根目录主进程模块**；角色人设走 `persona_host` 分节，**不用 `hostPersona`**（`dsh/gateway/gateway.mjs:1602` 会整段替换系统提示）。完整映射见 `docs/workspace/one-person-company/00-mtnode-integration.md`。

## 8. 验收口径

1. 同一问题在两个不同角色下运行，各自只看到自己的 L3，且都能引用 L1/L2 的相同依据。
2. 新增一条 L2 决策后，下一次任意角色的相关建议中出现该条目（检索命中），且带条目 id 与依据。
3. 矛盾结论并存时，建议输出显式提示冲突，而不是静默取一个。
4. 单次装配的上下文不超过预算表，超限按 §5.2 顺序裁剪且不裁 L0/L1。
5. 记忆库中不存在无 `evidence` 的 `high` 置信条目，也不存在密钥/凭据正文。
